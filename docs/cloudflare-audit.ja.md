# Cloudflareのストレージ・キュー監査

[English](cloudflare-audit.md) | [日本語](cloudflare-audit.ja.md)

2026-10-27にCloudflareの公式ドキュメントと照合した、ソースコード・設定の監査とローカル実行環境での検証です。本番アカウントの設定や稼働状態を確認したものではありません。

## 維持した設計

- **D1:** 値のバインド、冪等キーの一意制約、条件付きclaim、状態変更とイベントの同一トランザクションを維持。複数文の設定・送信バリアはD1のatomicなbatchを使う。結果不明のclaimを再実行しないよう、書き込み全体の自動retryは追加しない。通常のbinding呼び出しはprimaryを使い、Sessionsやread replicaの導入には認証・送信の整合性を別途検証する必要がある。
- **R2:** 非公開binding、原本を先に保存する順序、条件付き原本作成、復旧用メタデータ、解析済みオブジェクトを保存してからreadyにする順序を維持。復旧一覧はcustomMetadataを取得し、100件未満でも`truncated`と`cursor`に従う。原本・参照中の添付を自動削除しない。
- **Queues:** 本文を入れず識別子だけを運び、永続化後に個別ackする。再試行の遅延に上限を設け、両コンシューマーにDLQを設定する。投入・ackは宛先への配達成功を意味しない。Cronは永続化済みのpendingを独立して復旧する。
- **Durable Objects:** inbox単位の送信・無効化・webhook・復旧の直列化を維持。コンシューマーの並行数を増やしても、D1のバージョン付きバリアや外部呼び出し直前の同期所有権チェックは省略しない。

## 制約と運用

サポートする構成はWorkers Paidです。D1の呼び出し上限は現在Paidで1起動1,000クエリ、Freeで50です。原本復旧は1ページ100件以下で、従来の処理は1件最大4回のD1呼び出しとカーソル操作を使います。復旧のfan-out・検索件数も制限し、キューバッチは100件以下の小さい識別子だけなのでAPIの256 KB制限を下回ります。これは処理速度・遅延の保証ではありません。利用量に応じて本番のクエリ時間・読み書き行数・滞留時間・CPU時間を監視してください。

デプロイ前に`0009_recovery_indexes.sql`を含む全D1 migrationを適用します。大きいDBの索引作成には時間がかかるため、ステージング相当のデータで事前確認し、クエリ指標を確認してください。既存レコード・冪等キー・claimは残します。binding・キュー・DLQの名前は従来と互換で、新しいキューは不要です。

Cron失敗、`job_failed`、`job_attention_write_failed`、原本復旧の要対応状態、キューの滞留時間・retry・両DLQを監視します。Cloudflareのアラートと、認証付き`/v1/health`の外形監視を設定してください。コンシューマーのないDLQも保持期限があり、デフォルトは4日なので早めに取り出して調査します。自動replayは追加せず、特にunknownのメールはD1の状態と照合してください。アカウント側の保持設定を確認し、DLQをバックアップ扱いしないでください。

D1・R2の共通トランザクションや一括restoreはありません。Time TravelはR2・Durable Objectの状態を復元しません。bucketを非公開に保ち、原本・参照中の添付を消すlifecycleを避け、[復元時の注意点](operations.ja.md)に従ってください。オフサイトバックアップ・外部アラート登録・アカウント上限の確認・実メールの送受信確認は運用者側の作業であり、今回実行済みとはしていません。

## 検証

`test/cloudflare-storage.test.ts`と`test/queue-contracts.test.ts`で、実ローカルD1/R2、キューAPIの境界、不正body、失敗記録の障害分離、バッチ上限、復旧段階の独立性、保存サイズ超過、チェックサム保存、応答bodyの解放、実行計画を検証します。送信・受信・添付・webhookの既存モデルと実コードreplayも別途再実行します。[形式検証](formal-verification.ja.md)を参照してください。プラットフォーム上の時間・実過負荷・配達成功・プログラム全体の正しさは有限モデルの保証範囲外です。
