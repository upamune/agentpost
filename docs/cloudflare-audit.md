# Cloudflare storage and queue audit

[English](cloudflare-audit.md) | [日本語](cloudflare-audit.ja.md)

Reviewed on 2026-10-27 against Cloudflare's current documentation. This is a source/configuration audit and local-runtime verification; it does not establish the settings or health of a production account.

## Findings and changes

| Area                    | Finding                                                                                                                                                                  | Change                                                                                                                                                                                                                                                                                                                               |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Queue input             | TypeScript types did not validate runtime bodies. A null body could throw again in error logging and stop later jobs. An unknown kind could enter the inbound path.      | Strict kind-specific identifier validation. Invalid jobs retry toward the configured DLQ, without logging their bodies. Healthy jobs still receive individual acknowledgements.                                                                                                                                                      |
| Queue failure isolation | A failed D1 parsing-attention write escaped the per-message catch.                                                                                                       | Attention-write failures are logged separately; the original item retries and later items continue. Ready mail cannot be demoted.                                                                                                                                                                                                    |
| Recovery publication    | Three recovery scans each issued up to 100 separate queue sends. Mail publication exceptions were swallowed by the API-oriented helper, hiding unsuccessful Cron stages. | Each stage publishes up to 100 compact identifiers with `sendBatch`, reducing up to 300 queue calls to three. A failed batch rejects its stage, while other stages still run; retained D1/R2 work stays recoverable. Logs name failed stages.                                                                                        |
| D1 recovery             | Due-send ordering needed a temporary sort; stale sends, stale webhooks and message-to-webhook publication lacked matching indexes.                                       | Migration `0009_recovery_indexes.sql` replaces narrow due indexes and adds recovery/configuration indexes. Webhook recovery uses two indexed branches and a shared limit; forwarding recovery bounds each stale-state update at 100 rows. Real D1 `EXPLAIN QUERY PLAN` tests check index selection and absence of temporary sorting. |
| R2 reads                | Parsing, attachment extraction, replies and parsed-content retrieval could buffer retained objects without rechecking size.                                              | Preflight stored size and enforce the streamed byte limit: 10 MiB for MIME, 16 MiB for parsed JSON. Reject oversized retained data without deleting originals or committing readiness. Raw downloads continue streaming.                                                                                                             |
| R2 writes/resources     | Content digests were calculated but not supplied to R2 puts; rejecting attachment metadata could leave its body unread.                                                  | Native R2 SHA-256 upload validation for new originals and attachments. Cancel unused attachment bodies. Conditional create-only puts still preserve immutable admissions and uploads.                                                                                                                                                |
| Provider resources      | Non-success responses were left unread; success JSON was unbounded.                                                                                                      | Cancel unused error bodies and limit success responses to 64 KiB. An oversized/unreadable success response is **unknown**, never an automatic resend.                                                                                                                                                                                |
| Consumer scheduling     | One consumer serialized unrelated inboxes; a batch could parse five maximum-sized messages within one invocation's CPU budget.                                           | Mail consumers process one job per invocation, with at most four concurrent invocations; webhook consumers retain batches of five and concurrency four. Both queues wait at most one second to form a batch. This trades more invocations for bounded per-invocation work and cross-inbox progress.                                  |

## Existing safeguards retained

- **D1:** prepared/bound statements, database uniqueness for idempotency, conditional send/delivery claims, and transactional readiness/event triggers. Multi-statement dispatch/configuration barriers use atomic D1 batches. No app-wide write retry wrapper: an ambiguous committed claim must not be replayed as a new operation. Ordinary binding calls use the primary database; adding Sessions/read replicas would require a separate consistency review for authorization and dispatch.
- **R2:** private binding access, raw-before-index persistence, create-only immutable originals, recovery metadata, and parsed-put-before-ready ordering. Recovery requests custom metadata and follows `truncated`/`cursor`, even when a page contains fewer than its requested 100 objects. No automatic deletion of retained mail or referenced attachment objects.
- **Queues:** bodies contain identifiers only, individual acknowledgement follows durable processing, retry delay is bounded, and both consumers have dedicated DLQs. Queue publication/acknowledgement does not establish recipient delivery. Cron independently recovers pending durable work.
- **Durable Objects:** the named inbox coordinator still serializes sends, disabling, webhook dispatch and recovery. Increasing consumer concurrency does not remove per-inbox serialization, versioned D1 barriers or the final synchronous ownership fence.

## Limits and operations

Workers Paid is required by the supported deployment. D1 currently permits 1,000 queries per paid invocation versus 50 on Free. A raw-repair page remains bounded at 100 objects; the existing repair uses at most four D1 calls per object plus cursor operations. Recovery fan-out and publication scans are bounded, and each queue batch contains at most 100 small identifiers, well below the 256 KB API limit. These bounds are not a throughput or latency guarantee: measure production query duration, rows read/written, backlog age and CPU time as traffic grows.

Apply all D1 migrations, including `0009_recovery_indexes.sql`, before deploying. Index construction can take time on a large database; rehearse the migration against staging data and inspect query metrics. Existing rows, idempotency keys and send claims are retained. Resource names/bindings and DLQs stay compatible with the previous configuration; no additional queue is required.

Monitor Cron failures, `job_failed`, `job_attention_write_failed`, raw-recovery attention, queue backlog age, retries and both DLQs. Configure Cloudflare alerts and authenticated `/v1/health` monitoring for the deployment. A DLQ without an active consumer has finite retention (four days by default), so export/investigate it promptly. Do not attach an automatic replay consumer: reconcile the durable row first, especially unknown mail outcomes. Review queue retention in the account rather than treating a DLQ as a backup.

D1 and R2 still have no shared transaction or coordinated restore. Time Travel does not restore R2 or Durable Object state. Keep the bucket private, avoid lifecycle rules that expire retained originals or referenced attachments, and follow the [backup and restore precautions](operations.md). Offsite backups, external alert registration, account quota verification and real send/receive checks remain operator responsibilities; this change does not claim they ran.

## Evidence

`test/cloudflare-storage.test.ts` and `test/queue-contracts.test.ts` exercise real local D1/R2 plus queue API boundaries, malformed bodies, attention-write failure isolation, batch limits, independent recovery, oversized storage, checksum persistence, provider cleanup and query plans. Existing outbound, inbound, attachment and webhook models/replays are rerun separately; see [formal verification](formal-verification.md). Platform timing, real overload, provider delivery and whole-program correctness are outside those finite models.
