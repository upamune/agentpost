# Scorecard の改善と残る条件

[English](scorecard-remediation.md) | [日本語](scorecard-remediation.ja.md)

点数の背後にある改善と前提条件を記録します。完全な安全性の宣言ではありません。OpenSSF Scorecard は検出できる運用状況を測り、GitHub の運用項目につく重大度だけでは、アプリの悪用可能な脆弱性があるとは判断できません。条件が満たされるまで指摘は表示したままにします。

| 項目                   | 改善内容と残る前提                                                                                                                                                                                                                                                                                                                                               |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Fuzzing                | fast-check による 5 個のセキュリティ性質を全 PR・main・毎日に実行し、seed と縮小で再現します。最初の生成入力 50 万件は通過しました。[対象と再現方法](security-checks.ja.md#生成型のセキュリティ-fuzzing)を参照してください。                                                                                                                                     |
| 署名付きリリース       | ソース、7つの単体実行ファイル、npmアーカイブ、チェックサム、manifestにGitHub OIDC・SigstoreのSLSA来歴証明を付けます。ビルド・署名・公開を分け、13個の配布ファイルの完全な一覧、ソースのdigest、署名ワークフロー、保護したタグを検証してimmutableとして公開します。[検証手順](releases.ja.md)を参照してください。                                                 |
| ブランチ保護           | main は PR、最新 main への追随、会話の解決、セキュリティ・CI・形式検証と CodeQL の検出確認を必須にし、迂回主体を設けません。バージョンタグは所有者だけが作成でき、更新・削除は別ルールで禁止します。唯一のメンテナーは自分の PR を承認できないため、他者の承認はまだ必須にしていません。                                                                         |
| コードレビュー         | CODEOWNERS で変更をメンテナーに通知し、[貢献手順](../CONTRIBUTING.ja.md)にレビュー・テストの方針を記載しています。独立した承認、コード所有者、最終 push の承認を必須にするには、別の適格なメンテナーが必要です。過去の承認履歴は後から作れず、エージェントのレビューを人間のレビューとして扱いません。                                                           |
| 維持実績               | リポジトリの作成日は 2026-10-24 です。Scorecard は作成から 90 日未満のリポジトリを特別扱いします。この年齢条件はコードで変更できません。実際の保守を継続し、2027-01-22 以降に再確認します。                                                                                                                                                                      |
| OpenSSF Best Practices | [基準](https://www.bestpractices.dev/en/criteria/0)はプロジェクト登録と、開発者の知識・過去の応答実績を含む正確な申告を要求します。公開ソースと履歴、MIT、英日 API・導入・運用文書、issue、非公開報告、strict な検査、敵対的テスト、形式検証は用意しています。サイトのアカウントと、人・運用に関する申告の所有者確認が必要です。バッジや合格は宣言していません。 |
| パッケージ配布         | Node CLI/MCPは`@upamune/agentpost`として公開し、GitHub OIDC Trusted Publishingとnpm provenanceを使います。長期npm書込トークン、実行時依存、導入時スクリプトは使いません。検証済み単体実行ファイルはBunを内包します。Workerは各自でセルフホストし、来歴証明だけで本番設定や到達性を保証しません。                                                                 |

数値は[公開 Scorecard](https://scorecard.dev/viewer/?uri=github.com/upamune/agentpost)を参照してください。存在しないレビュアーの必須化、検査の非表示、他プロジェクトのバッジの流用、保守実績の捏造では安全性は改善しません。アカウント管理者はリポジトリルールを変更できるため、これらは所有者アカウント全体の侵害への対策ではありません。GitHub と Cloudflare では MFA を使い、管理者を絞ってください。
