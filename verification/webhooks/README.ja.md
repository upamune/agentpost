# Webhook と自動採番キーの形式検証

`mise run verify:webhooks` でモデル検査と、実際の Workers/D1 を使う 8 件の再現テストを実行します。`mise run verify:webhooks:selftest` は同じ正常系に加え、意図的に壊したモデル 12 種類と実装 5 種類を検出します。証跡は `.verification/webhooks/` に保存します。不変条件・アサーション違反は終了コード 1、ツール・設定の問題は 2 です。

## 性質と実装の対応

| モデル                | 守る性質                                                                                             | 対応する実装                                                                                                                       |
| --------------------- | ---------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| `Configuration.tla`   | 遅れて到着した古い設定更新が、完了済みの削除を復活させない。                                         | `src/webhook-store.ts` の `saveWebhook`。バージョン付き削除記録と条件付き D1 更新。                                                |
| `Delivery.tla`        | pending だけを取得し、古い結果で新しい取得を確定せず、交代済みアクターが古い宛先へ送信を開始しない。 | `src/webhook-delivery.ts` の取得・準備・送信・結果確定処理、`InboxCoordinator.serialize` と同期 SQLite フェンス。                  |
| `DispatchBarrier.tla` | 古い D1 更新の遅延到着や準備中のアクター交代が、開始するリクエストの設定を無効にしない。             | `src/dispatch-barrier.ts` の `webhookDispatchBarrier`、`InboxCoordinator` の配信・設定・有効状態更新、`fetch` 直前の最終フェンス。 |
| `Events.tla`          | ready 遷移で同じ受信箱の Webhook を不可分に記録し、設定変更で既存イベントの宛先を変更しない。        | `migrations/0006_inbox_webhooks.sql` のトリガー・一意制約、`prepare` の設定 ID を指定した取得。                                    |
| `Idempotency.tla`     | I/O 前にキーを決め、成功・失敗の両方で同じキーを返し、暗黙に再送しない。                             | `src/idempotency.ts` のキー解決・例外処理、`src/client.ts` の `MailClient.callSend`。CLI/MCP は通常テストでも確認。                |

`DispatchBarrier.tla` は `EmailOnly = TRUE` でも実行し、Webhook の設定変更を除外して、`outboundDispatchBarrier` が遅れて到着する受信箱の無効化を防ぐことも検査します。正常系は 5 モジュール・7 シナリオです。

自動採番と明示指定は、同じ状態機械を異なる入力で検査します。同じキーを再利用した際の D1 一意制約と本文ハッシュ比較は既存の添付検証が、送信メールの結果不明時に自動再送しない性質は既存の送信検証が別途確認します。

## 設計中に見つかった競合

古いコーディネーターが設定更新を開始し、D1 を待っている間に交代した場合、新しいコーディネーターが以前の設定を読んだ後に古い更新が完了する可能性がありました。新しいコーディネーター自身は所有権を持つため、最終フェンスだけでは古い設定での送信開始を止められません。

配信バリアは両方の順序を処理します。古い変更が先に完了すれば、バリアが準備済み設定を拒否します。バリアが先に完了すれば、設定と受信箱のバージョンを進めて古い更新を拒否します。バリア自身の待機中にも交代できるため、送信開始直前の同期フェンスも必要です。バリアに追い越された設定更新は、成功として通知せず競合を返します。

`DispatchBarrier.tla` はこれらの順序をまとめて探索します。`replays.test.ts` では実際の D1 更新を待機させ、バリアが古い更新を拒否することを確認します。実装のバリアを取り除くとアサーションが失敗します。8 件の再現では設定更新が先・バリアが先の両順序、受信箱の無効化、バリア待機中のコーディネーター交代を確認します。実行環境では本当の所有権分断を作れないため、2 つのインスタンスで実際の SQLite/D1 を共有し、仕様どおりの同期ストレージ拒否を注入します。

意図的に壊したモデルと修正済み実装の比較図を保存しています：[Webhook バリア](evidence/webhook-barrier/bug-1.png)、[Webhook 最終フェンス](evidence/webhook-fence/bug-1.png)、[メール送信バリア](evidence/outbound-barrier/bug-1.png)、[メール送信最終フェンス](evidence/outbound-fence/bug-1.png)。各ディレクトリに Mermaid、最短経路の説明、壊した `DispatchBarrier.cfg`、対応する正常系の `Guarded.cfg`、pstack の集計を保存しています。赤は意図的に壊した変異の不変条件違反、緑はガードを備えた実装にだけ存在する状態です。比較する両モデルの `EmailOnly` 設定は一致します。pstack の復号済みタプルは TLA+ に合わせた 1 始まりの添字です。正常系と変異の状態図はすべて作業用領域で描画・目視確認し、リポジトリにはこの 4 経路を残しています。

## 範囲と仮定

- 受信箱 2 個、各受信箱のメッセージ 1 件、配信取得 2 回、論理的な送信呼び出し 2 回。バリアの結合モデルではコーディネーター 3 世代と設定変更 2 回を扱います。
- D1 の文・バッチ・ready トリガー・一意制約は不可分と仮定します。SQLite フェンスの連番は単調増加し、所有権の拒否は同期的と仮定します。バリアの D1 待機と最終フェンスは別の遷移です。
- 有限モデル内の UUID 衝突はないと仮定し、暗号学的乱数そのものは証明しません。空・不正な明示キーの拒否は実装テストで確認します。
- Webhook は少なくとも 1 回の配信方式で、回復時も同じ配信 ID を使います。受信側の重複排除が必要です。設定変更時に既に進行中のリクエストは完了する場合があります。安全性の検証であり、必ず届くことや厳密に 1 回だけ届くことの証明ではありません。
- 配信モデルは代表的な 2 回の取得までです。任意回数の再試行・実時間・指数バックオフ・8 回上限の数値は証明せず、実装テストで確認します。
- AES-GCM/HMAC、暗号化データの結び付け、オリジン許可リスト、DNS/SSRF、TLS、HTTP 分類、応答サイズ、クライアントの表示契約は状態モデルの範囲外で、実装テストとレビューが必要です。
- 通常処理では ready は不変です。イベントモデルは pending から ready への不可分な遷移を扱い、運用者が SQL で ready を pending に戻す操作は扱いません。SQL の一意制約も永続化済みイベントの ID を保護します。

結果 JSON に検証対象の実装ハッシュを記録します。対象ファイルを変更したらモデルとの対応を確認してください。ハッシュは対象を示す証跡であり、対応関係を自動的に証明するものではありません。状態図の再生成と読み取りにはプロジェクトの `/statechart` スキルを、後続変更によるずれの調査には `/maintain-formal-verification-skill` を使います。
